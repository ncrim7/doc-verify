## Scope — read before quoting the number

100% synthetic documents — clean digitally-rendered PDFs from
`src/data_generation/document_generator.py`. No real / scanned / photographed
documents. Real-world accuracy is **not** measured. And, per the banner above,
this run does not cleanly measure model accuracy on synthetic data either,
because the generator did not print all the scored fields.

Do **not** put any number from this run into marketing, demo, or sales
material. It is superseded by the post-fix re-measurement.

## Defects

### D1 — silent extraction failure (2/60). The product-thesis failure.

`invoice_0017`, `po_0001`: HTTP 200, response would not parse as JSON.
`llm_extractor.extract()` returned `{}`; `run_full_pipeline.py:140` did
`if not extracted: ... continue` — so **verification never ran and nothing was
flagged**. In production, on a real document, the system would have said "all
good". That is the product's reason to exist collapsing.

Two layers, both must be fixed:

1. **Safety-net gap (the real bug).** Any empty / unparseable / structurally
   invalid extraction routes to REVIEW / human queue — generically, not tied to
   any one cause, never a silent skip, never an implicit "OK". Whatever
   production orchestrator gets built must not repeat `if not extracted: continue`.
2. **Immediate trigger.** gpt-5-nano is a reasoning model; `max_completion_tokens
   =4096` covers reasoning + output; on these two docs reasoning left too little
   for a full JSON object. Fix: `reasoning_effort="minimal"` (also cuts latency)
   + retry when `_parse_json_response` returns `None` + larger ceiling.

### D2 — data-generation rendering bugs (invalidate the score)

Verified in code (`document_generator.py:353–507`) and by extracting text from
all 60 rendered PDFs.

| # | Bug | Where | Effect on the corpus |
|---|---|---|---|
| 1 | **`currency` is never printed.** Amounts render as bare `f"{x:.2f}"`; no `gt["currency"]` / symbol anywhere in any `_render_*` method. | all three renderers | `currency` (GT `"TRY"`) absent from **60/60** pages. The model's `currency` field was scored on a value it could not read — it "passed" 52/58 by *guessing* TRY from Turkish context, "failed" 6 English-labelled docs by guessing USD. Not a model defect. |
| 2 | **Item-table body rows get no `FONTNAME`.** Style sets the Unicode font only for the header row `(0,0)-(-1,0)` and the totals block `(2,-3)-(-1,-1)`. Body rows fall back to ReportLab default `Helvetica`, which has Latin-1 (`ü ö ç`) but **not** `ğ ı ş İ`. | invoice/PO/receipt items tables | `Kağıdı`→`KaIIdI`, `Bandı`→`BandI`, `Çalışma`→`ÇalIIma`. **165/296** item descriptions do not appear on the page as written (`Dizüstü…` is fine — `ü` is Latin-1). |
| 3 | **`buyer_address` column too narrow.** Header table `colWidths=[35,65,35,35] mm`; `buyer_address` sits in the 35 mm column and ReportLab clips a plain string. `vendor_address` sits in the 65 mm column and fits. | invoice/PO header tables | `buyer_address` clipped on **39/40** invoices; `vendor_address` clean on 40/40. |

Net: `currency`, `description`, `buyer_address` — the three fields the earlier
draft of this report called "model errors" — are generator output bugs. The
model mostly read what was on the page correctly.

### D3 — what is left after D2 is removed

Genuine model slips look small: ~4 tax-id character errors (`Korutürk`→
`Korütürk`), a couple of `Spagetti`/`Spaghetti` normalisations. The real model
accuracy on correctly-rendered fields is well above 96.10% and will be measured
after the generator fix.

### D4 — self-verification added nothing here

Rule verifier: 0 issues, 0 auto-corrections, 0 correction-agent calls across
all 58. `arithmetic_repair` runs inside `extract()` so the math is already
consistent; gpt-5-nano populated every required field. Baseline == verified ==
corrected. Matches the thesis RQ3 finding — on clean data the verification
layer is a dirty-input QA net, not an accuracy lever.

## Note on the thesis numbers

The graduation-project figures (92.14% / 97.34%) were produced with this same
generator (the `tax_id` bug was fixed there; bugs 1–3 above were not). They
carry the same contamination. Historical — not something to fix now, but the
numbers are not directly comparable to a post-fix re-run.
