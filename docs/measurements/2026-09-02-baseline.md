# Measurement — 2026-09-02 · Phase-1 baseline

First authoritative accuracy run on the regenerated corpus. Single pass, no
tuning after seeing the result (per the project rule).

## Scope — read before quoting the number

This run is on **100% synthetic documents** — clean, digitally-rendered PDFs
produced by `src/data_generation/document_generator.py`. It contains **no real
documents** (no SROIE, no scanned or photographed invoices). It measures "how
well the pipeline does on the data it generates for itself", **not** "how well
it does on a customer's phone photo of a crumpled invoice". Those are different
claims. Real-world / degraded-input accuracy has **not** been measured yet
(Phase 2, P1-5).

Do **not** put this number (96.10% / 99.11% / etc.) into any marketing
material, demo copy, or sales conversation until D1 and D2 below are closed —
until then the number does not support the product's core claim ("the system
does not silently return a wrong answer").

## Setup

| | |
|---|---|
| Model | `gpt-5-nano` (strategy `direct`, `temperature` unset) |
| Pipeline | extract → rule-verify + auto-correct → correction-agent → evaluate |
| Corpus | 60 synthetic docs, `seed=42` (20 invoice / 20 PO / 20 receipt), `data/processed/measure_manifest.json` |
| Command | `python scripts/run_full_pipeline.py --model gpt-5-nano --strategy direct --split measure --delay 0.3 --checkpoint` |
| Runtime | ~23 min (~15–35 s/doc; gpt-5-nano is a reasoning model) |
| Cost | ~$0.05 estimated (~1.6k input + ~2k output tokens/call × 60). Exact figure in the Langfuse dashboard. |
| Raw result | `2026-09-02-baseline.results.json` (this folder) |

## Result

| Stage | Field-level EM | Semantic sim | Token F1 |
|---|---|---|---|
| Baseline (raw extraction) | **96.10%** | 99.11% | 97.92% |
| Verified (+ rule auto-correct) | 96.10% | 99.11% | 97.92% |
| Corrected (+ correction agent) | 96.10% | 99.11% | 97.92% |

- **58 of 60 docs** contributed; 2 produced no result (see Defects). Counting
  those 2 as 0% gives **92.9%**.
- Per type: invoice 96.0% (n=19) · PO 95.8% (n=19) · receipt 96.5% (n=20).
- Distribution: 20/58 docs scored a perfect 1.0; lowest was PO_0011 at 0.842.

**Semantic similarity 99.11% / token F1 97.92%** is the "is this usable"
signal — the extractions are almost entirely correct in meaning; strict EM is
lost on character-level Turkish-suffix differences (below).

## Defects found (→ Phase 2 backlog)

### D1 — silent extraction failure (2/60). The product-thesis failure.

`invoice_0017`, `po_0001`: HTTP 200, but the response would not parse as JSON.
`llm_extractor.extract()` returned `{}`; `run_full_pipeline.py:140` did
`if not extracted: ... continue` — so **verification never ran on these docs and
nothing was flagged**. The evaluation script only noticed because it compares
against ground truth. In production, on a real customer document, the system
would have said "all good". That is exactly the scenario the product exists to
prevent (it verifies its own output) collapsing.

Two layers, both must be fixed:

1. **Safety-net gap (the real bug).** Any empty / unparseable / structurally
   invalid extraction must route to a REVIEW verdict / human queue — never a
   silent skip and never an implicit "OK". This must be generic: not tied to
   the specific cause below. A future different model or document type will
   produce a broken output for some other reason, and the net must still catch
   it. No production orchestrator exists in this repo yet; whatever gets built
   must not repeat the `if not extracted: continue` pattern.
2. **Immediate trigger.** gpt-5-nano is a reasoning model; `max_completion_tokens
   =4096` covers reasoning + output, and on these two docs reasoning left too
   little for a complete JSON object. Fix: `reasoning_effort="minimal"` (also
   cuts the 15–35 s latency), a retry when `_parse_json_response` returns
   `None`, a larger ceiling.

Impact if unfixed: ~3.3% of documents skip verification silently.

### D2 — currency mislabelled `TRY` → `USD` (6/60 = 10%). Financial error.

On English-labelled docs (no ₺ symbol) the model labels a ₺1,000 amount as
$1,000. This is not a formatting nuisance like the truncations in D3 — it is a
wrong financial value the system reports with full confidence. For an
accounting-office user this is "the system gave me the wrong number and I
didn't know". Same severity as D1.

`SYSTEM_PROMPT` already has a currency rule; it is not enough for nano. Root
cause still open: locale/label detection failure, or a deeper
document-classification gap. Needs its own analysis, not a one-line prompt
tweak folded into D3.

### D3 — systematic truncation (the bulk of the ~4% EM gap)

Annoying, usually human-catchable, lower severity than D1/D2:

| Field | Misses (of 58) | Pattern |
|---|---|---|
| `description` | 46 | Turkish suffix dropped: `Ağ Anahtarı`→`Anahtar`, `Bandı`→`Band`, `Geniş`→`Geni`, `Deterjanı`→`Deterjan`, `Lisansı`→`Lisans`, `Dezenfektanı`→`Dezenfektan`. Also anglicisation: `Spagetti`→`Spaghetti`; quote mangling `(16'lı)`→`(16'')`. |
| `buyer_address` | 13 | Tail truncation: `…Suite 451, Erdoğ…` → `…Suite 45`. Check whether the dropped tail ever contains the city / postal code — if so this rises in severity. Long Faker US-format addresses fall below the 0.80 fuzzy-match threshold. |
| `vendor_tax_id` / `buyer_tax_id` | 4 | minor — occasional digit / Turkish-char slip (`Korutürk`→`Korütürk`). |

Note: the D2-era item catalog is deliberately Turkish-suffix-dense, which
maximised exposure to the `description` failure mode. Some misses
(`Spagetti`/`Spaghetti`) are near-synonyms a human reviewer would accept.

Fix candidates: a "copy the description verbatim, preserve every Turkish suffix,
do not translate or normalise" instruction; realistic Turkish address templates.

### D4 — self-verification added nothing here

Rule verifier: **0 issues, 0 auto-corrections, 0 correction-agent calls** across
all 58. `arithmetic_repair` runs inside `extract()`, so the math is already
consistent by the time the verifier sees it, and gpt-5-nano populated every
required field. Baseline == verified == corrected.

This matches the thesis finding (RQ3): on clean data the verification layer is
a production QA net for dirty input, not an accuracy lever. Its value shows on
degraded scans / real documents, not this synthetic set.
